# Requirements Document

## Introduction

This document defines the requirements for a comprehensive test suite for the Soma application. The test suite will provide automated testing coverage for services, API routes, validation schemas, and utility functions using Vitest as the testing framework. The suite will include unit tests, integration tests, and property-based tests to ensure code correctness, reliability, and maintainability.

## Glossary

- **Test_Framework**: Vitest - the testing framework used for running all tests
- **Test_Suite**: The complete collection of all test files and test cases
- **Unit_Test**: A test that verifies a single function or method in isolation
- **Integration_Test**: A test that verifies multiple components working together
- **Property_Test**: A test that verifies properties hold for randomly generated inputs
- **Test_Runner**: The Vitest process that executes tests and reports results
- **Mock**: A simulated object that replaces real dependencies during testing
- **Service_Layer**: Business logic modules in src/services/
- **DTO_Layer**: Zod validation schemas in src/dtos/
- **API_Layer**: Next.js API route handlers in src/app/api/
- **Prisma_Client**: The database ORM client used for data access
- **Test_Coverage**: Percentage of code executed by tests
- **Assertion**: A statement that verifies expected behavior in a test

## Requirements

### Requirement 1: Test Framework Setup

**User Story:** As a developer, I want a properly configured test framework, so that I can write and run tests efficiently.

#### Acceptance Criteria

1. THE Test_Framework SHALL be Vitest with React plugin and jsdom environment
2. THE Test_Framework SHALL support TypeScript with path aliases (@/ imports)
3. THE Test_Framework SHALL provide coverage reporting capabilities
4. THE Test_Framework SHALL execute tests in isolation without side effects
5. WHERE a test file is specified, THE Test_Runner SHALL execute only that test file
6. WHERE a test name is specified, THE Test_Runner SHALL execute only that specific test

### Requirement 2: Service Layer Unit Tests

**User Story:** As a developer, I want comprehensive unit tests for all service functions, so that I can verify business logic correctness.

#### Acceptance Criteria

1. WHEN testing auth.service functions, THE Test_Suite SHALL mock the Prisma_Client
2. WHEN testing auth.service functions, THE Test_Suite SHALL mock bcrypt and jsonwebtoken
3. WHEN testing operation.service functions, THE Test_Suite SHALL verify CRUD operations
4. WHEN testing project.service functions, THE Test_Suite SHALL verify CRUD operations and ownership validation
5. WHEN testing creative.service functions, THE Test_Suite SHALL verify CRUD operations and decimal handling
6. IF a service function throws an AppError, THEN THE Test_Suite SHALL verify the error type and message
7. THE Test_Suite SHALL verify that service functions return expected data types

### Requirement 3: Validation Schema Property Tests

**User Story:** As a developer, I want property-based tests for validation schemas, so that I can ensure schemas handle edge cases correctly.

#### Acceptance Criteria

1. FOR ALL valid email strings, parsing with loginSchema SHALL succeed
2. FOR ALL invalid email strings, parsing with loginSchema SHALL fail with appropriate error
3. FOR ALL valid CPF strings, parsing with registerSchema SHALL succeed
4. FOR ALL invalid CPF strings, parsing with registerSchema SHALL fail with appropriate error
5. FOR ALL decimal values in valid range, parsing with createCreativeSchema SHALL succeed
6. FOR ALL pagination parameters where page >= 1 and limit <= 100, parsing with paginationSchema SHALL succeed
7. FOR ALL pagination parameters where page < 1 or limit > 100, parsing with paginationSchema SHALL fail

### Requirement 4: Round-Trip Property Tests

**User Story:** As a developer, I want round-trip tests for data transformations, so that I can verify serialization and deserialization correctness.

#### Acceptance Criteria

1. FOR ALL valid RegisterDto objects, encoding to JSON then decoding SHALL produce equivalent objects
2. FOR ALL valid decimal values, transforming with decimalTransform then converting back SHALL preserve the value
3. FOR ALL valid JWT tokens generated by auth.service, verifying the token SHALL return the original payload data

### Requirement 5: API Route Integration Tests

**User Story:** As a developer, I want integration tests for API routes, so that I can verify end-to-end request handling.

#### Acceptance Criteria

1. WHEN testing POST /api/auth/register with valid data, THE Test_Suite SHALL verify successful user creation
2. WHEN testing POST /api/auth/login with valid credentials, THE Test_Suite SHALL verify token generation
3. WHEN testing authenticated routes without a token, THE Test_Suite SHALL verify 401 response
4. WHEN testing authenticated routes with an invalid token, THE Test_Suite SHALL verify 401 response
5. WHEN testing CRUD operations on operations, THE Test_Suite SHALL verify proper HTTP status codes
6. WHEN testing CRUD operations on projects, THE Test_Suite SHALL verify proper HTTP status codes
7. WHEN testing CRUD operations on creatives, THE Test_Suite SHALL verify proper HTTP status codes
8. IF an API route returns an error, THEN THE Test_Suite SHALL verify RFC 9457 problem details format

### Requirement 6: Error Handling Tests

**User Story:** As a developer, I want tests for error handling, so that I can verify errors are properly formatted and handled.

#### Acceptance Criteria

1. WHEN an AppError is thrown, THE Test_Suite SHALL verify it contains type, title, status, and detail fields
2. WHEN handleError processes an AppError, THE Test_Suite SHALL verify it returns application/problem+json response
3. WHEN a service throws problems.resourceNotFound, THE Test_Suite SHALL verify status is 404
4. WHEN a service throws problems.invalidCredentials, THE Test_Suite SHALL verify status is 401
5. WHEN a service throws problems.emailAlreadyExists, THE Test_Suite SHALL verify status is 409
6. THE Test_Suite SHALL verify that error responses include the instance field with request path

### Requirement 7: Authentication Middleware Tests

**User Story:** As a developer, I want tests for authentication middleware, so that I can verify token extraction and validation.

#### Acceptance Criteria

1. WHEN a request has a valid Bearer token, THE authenticate function SHALL return user information
2. WHEN a request has no Authorization header, THE authenticate function SHALL throw invalidToken error
3. WHEN a request has an invalid Bearer token format, THE authenticate function SHALL throw invalidToken error
4. WHEN a request has an expired token, THE authenticate function SHALL throw invalidToken error
5. THE Test_Suite SHALL verify extractBearerToken correctly extracts tokens from Authorization headers

### Requirement 8: Utility Function Tests

**User Story:** As a developer, I want tests for utility functions, so that I can verify helper function correctness.

#### Acceptance Criteria

1. WHEN testing cn() with multiple class names, THE Test_Suite SHALL verify proper class merging
2. WHEN testing cn() with conditional classes, THE Test_Suite SHALL verify correct output
3. WHEN testing extractBearerToken with valid header, THE Test_Suite SHALL verify token extraction
4. WHEN testing extractBearerToken with invalid header, THE Test_Suite SHALL verify null return

### Requirement 9: Database Mock Configuration

**User Story:** As a developer, I want properly configured database mocks, so that tests run without requiring a real database.

#### Acceptance Criteria

1. THE Test_Suite SHALL mock the Prisma_Client for all service tests
2. THE Test_Suite SHALL provide mock implementations for findUnique, findMany, create, update, and delete
3. WHEN a test requires specific database state, THE Test_Suite SHALL configure mocks to return appropriate data
4. THE Test_Suite SHALL reset all mocks between test cases to prevent side effects
5. THE Test_Suite SHALL verify that service functions call Prisma methods with correct parameters

### Requirement 10: Test Organization and Structure

**User Story:** As a developer, I want well-organized test files, so that I can easily locate and maintain tests.

#### Acceptance Criteria

1. THE Test_Suite SHALL place test files adjacent to source files with .test.ts extension
2. THE Test_Suite SHALL use describe blocks to group related tests
3. THE Test_Suite SHALL use descriptive test names that explain what is being tested
4. THE Test_Suite SHALL follow the Arrange-Act-Assert pattern in test implementations
5. THE Test_Suite SHALL include setup and teardown functions where needed
6. THE Test_Suite SHALL document complex test scenarios with comments

### Requirement 11: Test Execution Commands

**User Story:** As a developer, I want convenient commands to run tests, so that I can execute tests during development.

#### Acceptance Criteria

1. THE Test_Suite SHALL provide a command to run all tests
2. THE Test_Suite SHALL provide a command to run tests in watch mode
3. THE Test_Suite SHALL provide a command to run tests with coverage reporting
4. THE Test_Suite SHALL provide a command to run a single test file
5. THE Test_Suite SHALL provide a command to run a single test by name
6. WHEN tests complete, THE Test_Runner SHALL display pass/fail status and execution time

### Requirement 12: Coverage Requirements

**User Story:** As a developer, I want to track test coverage, so that I can identify untested code.

#### Acceptance Criteria

1. THE Test_Framework SHALL generate coverage reports for all source files
2. THE Test_Framework SHALL report line coverage, branch coverage, and function coverage
3. THE Test_Framework SHALL exclude test files from coverage calculations
4. THE Test_Framework SHALL exclude configuration files from coverage calculations
5. WHERE coverage falls below thresholds, THE Test_Runner SHALL report which files need more tests
